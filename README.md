# UpdateManager

**UpdateManager** — Windows-утилита для выпуска обновлений приложения: патчи Windows с помощью **SimplePatchTool** и встроенного **SelfPatcher**, а также выкладка Android-сборок с подписью файлов.

Приложение помогает подготовить проект обновлений, добавить новые версии билда, собрать патч (Windows) или подписать файлы (Android) и доставить их в локальную папку или на FTP-сервер.

## Возможности

* Создание проекта обновлений; открытие существующего; стартовый экран с тремя последними проектами.
  Правый клик по проекту на стартовом экране: **Убрать из списка** — только из показа, **Удалить проект…** —
  папка проекта целиком в Корзину.
* Каталог выпусков: каждая версия — запись с этапами **Билд → Патч → Доставка → Проверка**,
  состояние каждого этапа видно сразу (дата, способ доставки, причина провала).
* Повтор любого пройденного этапа последнего выпуска (пересобрать ту же версию, доставить или проверить снова);
  следующие этапы при этом сбрасываются.
* Автоматическое определение версии билда по `FileVersion` главного `.exe` (или по `<Product>_vers.sptv`).
* Сборка repair / installer / incremental патчей.
* Поддержка self-patching приложения через встроенный self-patcher.
* Доставка готового патча в локальную папку или на FTP-сервер (с обзором папок сервера).
* Проверка опубликованного патча: настоящая закачка через `VersionInfo.info`, как у клиента.
* RSA-подпись патча.
* Платформа **Android** (включается в настройках проекта): без патчей — подпись файлов по маске RSA-ключом
  проекта, выкладка в канал `AndroidPatch`, проверка канала. Можно выпускать Windows и Android вместе или по одной.
* Самообновление самого UpdateManager (проверка при запуске и из меню).
* Светлая, тёмная тема и «как в Windows».

## Требования

* Windows 10/11 x64. Готовая сборка self-contained — .NET ставить не нужно.
* Для сборки из исходников: .NET SDK 10.
* Библиотеки движка в папке `lib` (`SimplePatchTool.dll`, `SimplePatchToolSecurity.dll`);
  остальные зависимости (Avalonia, FluentFTP, …) подтягиваются из NuGet.

Версия 1.x (WinForms, .NET Framework 4.8) — ветка `v1`, тег `v1.0.3`.

## Сборка проекта

1. Склонируйте репозиторий:

```bash
git clone https://github.com/BorisBaNaNa/UpdateManager.git
```

2. Соберите и запустите тесты (или откройте `UpdateManager.sln` в Rider / Visual Studio):

```bash
dotnet build UpdateManager.sln
dotnet test tests/UpdateManager.Tests
```

3. Запуск из исходников:

```bash
dotnet run --project src/UpdateManager.App
```

4. Сборка для выкатки (self-contained, win-x64):

```bash
dotnet publish src/UpdateManager.App -p:PublishProfile=win-x64
```

Результат — в `Release/` в корне репозитория (`UpdateManager.exe` + DLL + рантайм + `SPPatcher/` со встроенным self-patcher'ом); папка очищается перед каждым publish. Из неё же UpdateManager собирает патч сам себе.

### Выпуск новой версии

0. Заметки выпуска — `docs/releases/X.Y.Z.md` (формат как у `docs/releases/2.0.0.md`). Они вшиваются
   в программу (окно «Что нового») и идут в GitHub Release; без них скрипт выпуск не соберёт.
1. `scripts/release.ps1`: тесты → подъём версии в `Directory.Build.props` → publish в `Release/` →
   version holder `Release/UpdateManager_vers.sptv` (клиент проверяет обновления по нему, не сверяя файлы) →
   сверка `FileVersion` и наличия `SPPatcher/SelfPatcher.exe`:

   ```bash
   powershell.exe -ExecutionPolicy Bypass -File scripts/release.ps1 patch    # 2.0.0 → 2.0.1
   powershell.exe -ExecutionPolicy Bypass -File scripts/release.ps1 minor    # 2.0.1 → 2.1.0
   powershell.exe -ExecutionPolicy Bypass -File scripts/release.ps1 -NoBump  # пересобрать текущую
   ```

   Скрипт ничего не коммитит. Новая возможность → minor, иначе patch.
2. В самом UpdateManager: патч из `Release/` → доставка → «Проверить».
3. Коммит подъёма версии и **тег git** `vX.Y.Z` (аннотированный, на коммите, из которого собран
   `Release/`), например `git tag -a v2.0.0 -m "UpdateManager 2.0.0"`; push `main` и тега.
4. GitHub Release — тем же скриптом (нужен [GitHub CLI](https://cli.github.com/) со входом, `gh auth login`):

   ```bash
   powershell.exe -ExecutionPolicy Bypass -File scripts/release.ps1 -Publish
   ```

   Ничего не собирает: проверяет, что в `Release/` текущая версия и тег запушен, и публикует выпуск
   «UpdateManager vX.Y.Z.0» с текстом `docs/releases/X.Y.Z.md` и архивом `Release/` (`UpdateManager.vX.Y.Z.zip`).
   Архив собирается во временной папке и удаляется после отправки.

Структура репозитория:

```text
src/UpdateManager.Core/    доменный слой: проекты, сборка/проверка, доставка, подпись, самообновление
src/UpdateManager.App/     UI на Avalonia (Views / ViewModels / Services)
tests/UpdateManager.Tests/ тесты xUnit
lib/                       DLL движка SimplePatchTool
```

## Главное окно

Без открытого проекта — стартовый экран: последний проект крупно (его этапы и кнопка **Открыть**)
и список недавних.

С проектом слева — каталог выпусков (версия, «№ N · состояние» и мини-полоса этапов), справа — выбранный
выпуск: номер версии, блоки этапов и одна главная кнопка следующего шага («Создать патч», «Доставить»,
«Проверить»). Ниже — сведения проекта: папка билда, главный `.exe`, сервер, доставка, папка проекта.

Блоки этапов:

* залитый цветом — этап пройден;
* контур — ещё нет (или «устарела: …», если после него повторили предыдущий этап);
* красный контур — провал (например, проверка не прошла), причина — в блоке и в подсказке.

Блоки **последнего** выпуска нажимаются: пройденный этап можно повторить, следующий — выполнить.
Повтор сбрасывает следующие этапы: пересобранный патч считается не доставленным и не проверенным,
доставленный заново — не проверенным. Старые выпуски только для просмотра. Те же действия — в меню **Выпуск**.

Блок **Билд** — вход извне: сам билд собирается вне UpdateManager (IDE, скрипт). Блок показывает,
откуда он взят, а нажатие меняет папку билда. Если в папке билда появилась версия новее собранных,
в каталоге появляется запись «новый».

## Основной сценарий использования

### 1. Создание проекта обновлений

1. Запустите `UpdateManager.exe`.
2. Нажмите **Создать проект…** (стартовый экран или меню **Проект**).
3. Выберите папку, в которой будет храниться проект обновлений.
4. Введите имя проекта.

После создания в выбранной папке появятся служебные файлы и директории проекта:

```text
Settings.xml
Versions/
Output/
SelfPatcher/
Other/
updatemanager.project.xml
```

> Не рекомендуется создавать проект обновлений внутри папки с билдом приложения. Папка проекта должна быть отдельной.

## 2. Настройка проекта

Откройте настройки проекта (строка **Сервер → Настройки…** или меню **Проект**) и заполните основные параметры.
Адрес сервера и директория загрузки складываются в `BaseDownloadURL` — итоговый адрес виден прямо под полями.

### BaseDownloadURL

`BaseDownloadURL` — базовый URL, по которому клиентское приложение будет скачивать файлы патча.

Пример:

```text
https://example.com/patches/MyApp/
```

Важно: этот URL встраивается в патч во время сборки. Если изменить `BaseDownloadURL` после сборки, патч нужно собрать заново.

### Типы патчей

Можно включить один или несколько типов патчей:

* **Repair Patch** — полный патч для восстановления файлов.
* **Installer Patch** — патч для установки.
* **Incremental Patch** — инкрементальный патч между версиями.

Для обычного обновления приложения чаще всего нужен **Incremental Patch**. Для большей надёжности можно дополнительно включить **Repair Patch**.

### Self Patching App

Включите `IsSelfPatchingApp`, если приложение должно обновлять само себя.

При создании проекта UpdateManager автоматически копирует встроенный self-patcher в папку проекта `SelfPatcher/`;
при сборке патча движок кладёт его в патч, и у клиентов он лежит в `SPPatcher/`.

Если в качестве билда выбран сам UpdateManager (совпали `ProductName` и `CompanyName` главного `.exe`), программа предложит применить настройки самообновления: включить `IsSelfPatchingApp`, взять `BaseDownloadURL` из своего `appsettings.json` и добавить в `IgnoredPaths` `*.pdb`, `*.vshost.*` и логи движка.

## 3. Выбор папки билда

1. Нажмите **Выбрать…** в строке **Папка билда** (или блок **Билд**, или меню **Выпуск → Папка билда…**).
2. Укажите папку с готовым билдом приложения.
3. UpdateManager попробует найти главный `.exe` и прочитать его `FileVersion`.

По умолчанию главный исполняемый файл ищется по имени проекта:

```text
<ИмяПроекта>.exe
```

Например:

```text
MyApp.exe
```

Если главный `.exe` называется иначе, выберите его вручную: строка **Главный exe → Выбрать…**.

## 4. Версия билда

Версия берётся из `FileVersion` главного `.exe`, а если в папке билда есть version holder движка
`<ИмяПроекта>_vers.sptv` — из него. Перед сборкой версию можно подтвердить или исправить.

Допустимый формат версии:

```text
1.0.0.0
```

Версия должна состоять только из чисел, разделённых точками.

Недопустимые примеры:

```text
v1.0
1.2-beta
1.0.0f1
```

Новая версия не должна быть ниже уже собранной максимальной версии, потому что инкрементальные патчи строятся по возрастанию версий.

## 5. Создание патча

1. Выберите папку билда.
2. Нажмите **Создать патч** (главная кнопка или блок **Патч**).
3. Подтвердите или введите версию.
4. Дождитесь завершения операции: окно показывает ход сборки, итог словами и причину ошибки, если она есть.

Чтобы пересобрать ту же версию (например, после правки настроек), нажмите блок **Патч** → **Пересобрать**.

UpdateManager скопирует билд в:

```text
Versions/<version>/
```

Затем SimplePatchTool соберёт патч в папку:

```text
Output/
```

Например:

```text
Versions/1.0.0.0/BuildFiles...
Output/PatchFiles...
```

## 6. Доставка патча

После успешной сборки патч нужно доставить туда, откуда клиентское приложение сможет его скачать.

Нажмите **Доставить** (главная кнопка или блок **Доставка**) и выберите способ доставки. Способ и путь можно
настроить заранее, без доставки: строка **Доставка → Настроить…**. Время доставки запоминается по версиям.

Доставка **зеркальная**: после успешной отправки в папке назначения остаётся ровно новый патч, всё старое
удаляется. Сохраняется только папка канала Android (`AndroidPatch`) — она выкладывается отдельно.

### Доставка в локальную папку

Выберите метод:

```text
Папка (локальный путь)
```

Затем укажите папку назначения.

UpdateManager скопирует содержимое `Output/` в выбранную папку.

Этот вариант удобно использовать, если вы вручную загружаете файлы на сервер или тестируете патчи локально.

### Доставка на FTP

Выберите метод:

```text
FTP (сервер)
```

Параметры подключения задаются в меню **Выпуск → FTP-сервер…** (если их нет, окно откроется само при доставке):

* хост и порт;
* логин и пароль;
* папка с патчами на сервере (кнопка **Выбрать…** открывает обзор папок сервера);
* отдельная закрытая папка для приватного RSA-ключа (необязательно).

Итоговый путь загрузки = папка с патчами + директория загрузки проекта. UpdateManager загрузит туда
содержимое `Output/`. Кнопка **Проверить соединение** проверяет реквизиты до доставки.

Пароль FTP сохраняется в защищённом виде через механизм Windows DPAPI. Если открыть проект на другом компьютере или под другой учётной записью Windows, пароль может потребоваться ввести заново.

## 7. Проверка патча

После публикации можно выполнить проверку.

Проверка использует URL:

```text
<BaseDownloadURL>/VersionInfo.info
```

Например:

```text
https://example.com/patches/MyApp/VersionInfo.info
```

UpdateManager скачивает патч во временную папку так же, как это сделает клиент, и проверяет, что опубликованные
файлы доступны. Итог запоминается: блок **Проверка** станет зелёным или красным с причиной.

Проверка идёт по публичному адресу сервера. Если роутер не поддерживает NAT loopback, изнутри локальной сети
этот адрес недоступен и проверка завершится таймаутом — проверяйте из внешней сети.

## Android

Включите платформу в настройках проекта: **Платформы → Android**. Там же задаются:

* **Канал на сервере** — папка внутри папки патча, по умолчанию `AndroidPatch`. Публичный адрес канала —
  `BaseDownloadURL` + канал (виден под полем).
* **Подписывать** — флажок «Подписывать файлы RSA-ключом» и маски файлов от папки билда, по одной в строке
  (`latest.json`, `*.apk`, `manifests/*.json`). Без подписи (как без «Подписывать патч» у Windows) этап
  называется **Версия**: он только записывает версию выпуска, ключ не нужен, `.sig` в канал не уходят.
* **Не выкладывать** — маски файлов, которые не уходят на сервер (например, сборка для эмулятора).

Сам apk собирается вне UpdateManager. Порядок:

1. **Папка Android → Выбрать…** — папка билда (apk, манифест).
2. **Подписать файлы** — UpdateManager спросит версию выпуска (из файлов он её не читает) и подпишет файлы по
   маскам тем же RSA-ключом проекта, что и патчи Windows: SHA-256, PKCS#1 v1.5, по сырым байтам. Рядом с каждым
   файлом появится `<файл>.sig` (base64, UTF-8 без BOM). Подпись сразу сверяется с публичным ключом; маска без
   совпадений — ошибка.
3. **Доставить** — все файлы папки билда, кроме «не выкладывать» и чужих `.sig`, уходят в канал тем же способом,
   что и патч (папка или FTP). Канал подменяется целиком: подписанный манифест и подпись появляются разом,
   старое удаляется. Файл, изменённый после подписи, выкладывать нельзя — подпишите заново.
4. **Проверить** — скачать выложенное по публичному адресу, сверить байты с папкой билда и подписи с публичным ключом.

Версия Android, совпавшая с версией Windows, — один выпуск с двумя полосами этапов. Подпись самого apk
(keystore) — забота сборки, UpdateManager её не трогает.

## 8. Самообновление UpdateManager

UpdateManager умеет обновлять сам себя тем же движком.

* При запуске программа тихо проверяет обновления. Если сервер недоступен — ничего не показывает. Под отладчиком автопроверка отключена.
* Вручную: **Справка → Проверить обновления…** — всегда покажет результат или ошибку.
* После обновления программа один раз сама показывает окно **Что нового** с заметками новых выпусков.
  Открыть его в любой момент — **Справка → Что нового…**.
* Если есть новая версия, программа предложит обновиться, скачает патч в окне прогресса и предложит перезапуск. Файлы подменяет self-patcher (`SPPatcher/SelfPatcher.exe`) после закрытия программы, затем запускает её снова.

Настройки — в `appsettings.json` рядом с `UpdateManager.exe`:

```json
{
  "SelfUpdate": {
    "VersionInfoUrl": "https://updates.borealis-soft-home.duckdns.org:51943/UpdateManager/VersionInfo.info",
    "PublicKey": ""
  }
}
```

* Пустой `VersionInfoUrl` — самообновление выключено.
* `PublicKey` — содержимое `public.key` проекта; если задан, неподписанный или подделанный патч будет отвергнут.

Чтобы выпустить новую версию самого UpdateManager: соберите её `scripts/release.ps1` (см. «Выпуск новой версии»),
откройте проект обновлений UpdateManager (при первом выборе билда примите предложенный пресет), соберите патч из
`Release/`, доставьте его в папку, на которую указывает `VersionInfoUrl`, проверьте и поставьте тег.

## Рекомендуемый порядок работы

1. Собрать новую версию приложения.
2. Убедиться, что у главного `.exe` выставлен корректный `FileVersion`.
3. Открыть проект в UpdateManager.
4. Выбрать папку нового билда.
5. Проверить определённую версию.
6. Создать патч.
7. Доставить патч в папку или на FTP.
8. Выполнить проверку опубликованного патча.

## Важные ограничения

* Папка билда не должна совпадать с папкой проекта обновлений или находиться внутри неё.
* `BaseDownloadURL` должен быть задан до сборки патча.
* После изменения настроек проекта патч нужно пересобрать.
* Версии должны идти по возрастанию.
* Формат версии должен быть числовым.
* Для self-patching приложения в проекте должен присутствовать `SelfPatcher`.

## Структура проекта обновлений

Пример структуры после создания проекта:

```text
MyUpdateProject/
├── Settings.xml
├── updatemanager.project.xml
├── Versions/
│   ├── 1.0.0.0/
│   └── 1.0.1.0/
├── Output/
├── SelfPatcher/
│   ├── SelfPatcher.exe
│   └── SelfPatcherCore.dll
└── Other/
```

### Settings.xml

Основной файл настроек SimplePatchTool.

### updatemanager.project.xml

Дополнительный файл UpdateManager: главный `.exe`, последняя папка билда, способ доставки и по каждой версии —
когда собран патч, когда доставлен и итог проверки. Реквизиты FTP здесь не хранятся: они в профиле пользователя
(`%AppData%\UpdateManager\ftp.xml`, пароль зашифрован DPAPI).

### Versions/

Папка с сохранёнными версиями приложения.

Каждая версия хранится в отдельной подпапке:

```text
Versions/1.0.0.0/
Versions/1.0.1.0/
```

### Output/

Папка с готовыми файлами патча после сборки.

Именно содержимое этой папки нужно публиковать на сервере.

### SelfPatcher/

Папка со встроенным self-patcher'ом, который нужен для обновления self-patching приложения. При сборке патча
движок кладёт его в патч как `SPPatcher/`.

## Частые ошибки

### Не задан BaseDownloadURL

Перед сборкой патча нужно указать `BaseDownloadURL` в настройках проекта.

Без него клиентское приложение не сможет скачать файлы обновления.

### UpdateManager не нашёл версию

Проверьте, что:

* выбран правильный билд;
* главный `.exe` находится в папке билда;
* имя `.exe` совпадает с именем проекта или выбран вручную;
* у `.exe` заполнен `FileVersion`.

### Версия недопустима

Используйте только числовой формат:

```text
1.0.0.0
```

Не используйте буквы, префиксы и суффиксы.

### Версия ниже уже собранной

Нельзя собрать версию ниже максимальной версии из `Versions/`.

Например, если уже есть:

```text
1.0.2.0
```

то версия:

```text
1.0.1.0
```

будет отклонена.

### Output пустой

Сначала нужно создать патч. Только после этого его можно доставить.

### Проверка висит и падает по таймауту

Сервер недоступен с этого компьютера. Частая причина — проверка изнутри локальной сети, когда роутер не
пускает на собственный публичный адрес (нет NAT loopback). Повторите проверку из внешней сети.
