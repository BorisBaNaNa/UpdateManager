# CLI выпуска (`umcli`) — дизайн

Статус: **спецификация, не начато.** Плановая версия — 2.2.0 (новая возможность → minor; 2.1.0 — платформа Android). Команды учесть
трек Android (`patch` → для Android подпись `sign`), когда дойдёт до реализации.

## Цель

Выпуск без окна: агент (Claude Code), `scripts/release.ps1`, планировщик или CI одной командой
собирают патч из билда, доставляют его и проверяют — с теми же защитами и той же записью состояния,
что и главное окно.

Успех: после `scripts/release.ps1 minor` одна команда `umcli release …` доводит выпуск до «проверен»,
а открытый потом UpdateManager показывает этот выпуск в каталоге с теми же датами этапов, как если бы
его делали руками.

## Решения

| Вопрос | Решение |
|---|---|
| Форма API | Консольная программа с JSON-выводом и кодами выхода. MCP-сервер — позже и только тонкой обёрткой над CLI, если понадобится |
| Где логика выпуска | Выносится из `MainWindowViewModel` в Core (`Core/Release/`); окно и CLI — два клиента одного сервиса |
| Сборка | Отдельный консольный проект `src/UpdateManager.Cli` → `umcli.exe` (`UpdateManager.exe` — WinExe, его stdout не виден в консоли). Кладётся в `Release/` рядом с `UpdateManager.exe` и входит в патч |
| Вопросы окна | Становятся флагами. Без флага там, где окно спрашивает, CLI **отказывает** с понятной ошибкой, а не соглашается молча |
| FTP-реквизиты | Те же `%AppData%\UpdateManager\ftp.xml` (DPAPI, текущая учётка Windows). В аргументах и выводе пароля нет никогда |
| Состояние | Тот же `updatemanager.project.xml` (`PatchedVersions`, `DeliveredVersions`, `VerifiedVersions`) и тот же сброс следующих этапов при повторе |
| Прогресс | Строки лога движка — в stderr; итог — в stdout (текст или `--json`) |

## Шаг 1. Сервис выпуска в Core (основная работа)

Сейчас Core не знает про UI, но весь сценарий выпуска живёт в `MainWindowViewModel`. Переносим в Core
(`UpdateManager.Core.Release`, стиль Core: блочные namespace, без nullable):

- **Защиты сборки** (`CreatePatch`): папка билда существует и не пересекается с проектом; непустой
  `BaseDownloadURL`; выбран хотя бы один тип патча; не-ASCII имена при installer-патче; билд самого
  UpdateManager без `IsSelfPatchingApp`; версия валидна (`VersionRules`), не ниже максимальной, при
  равной — перезапись.
- **Сборка**: `ResetStagesFrom(Patch)` → `StageBuild` → `PatchBuilder` → подпись (`PatchSigner`, если
  `SignPatch`) → отпечаток настроек (`LastBuiltSettings`) → `PatchedVersions`.
- **Доставка** (`Deliver`/`DeliverViaFtp`): Output не пуст; предупреждение «настройки менялись после
  сборки»; `ResetStagesFrom(Delivery)` → папка (`DeliveryFactory`) или FTP (`FtpUploadOperation`) →
  `DeliveredVersions`.
- **Проверка** (`Verify`): `PatchVerifier` во временную папку → `VerifiedVersions`.
- **Статус**: модель выпуска (`ReleaseCatalog`) переезжает из `App/ViewModels` в Core без
  Avalonia-зависимостей (свойства отображения — `IsActionable`, тексты кнопок — остаются в App).

Каждая защита возвращает типизированный результат (`Blocked` — нельзя; `NeedsConfirmation` — окно
спросит, CLI требует флаг), а не показывает диалог. Окно переводит `NeedsConfirmation` в
`ConfirmAsync`, CLI — в ошибку с подсказкой флага. Длинные операции остаются `IEngineOperation`:
окно крутит их в окне операции, CLI — опросом с выводом лога.

Готовность шага: окно работает через сервис, все текущие тесты VM зелёные, у сервиса свои тесты
(защиты, сброс этапов, запись дат) без VM.

## Шаг 2. Команды

```
umcli status  --project <папка> [--json]
umcli patch   --project <папка> [--build <папка>] [--version X.Y.Z.W] [--overwrite] [--allow-self-without-selfpatching] [--allow-non-ascii]
umcli deliver --project <папка> [--allow-stale-settings] [--dry-run]
umcli verify  --project <папка> [--timeout <сек>]
umcli release --project <папка> [--build <папка>] [--version …] [--overwrite] --deliver --verify [--dry-run]
```

- `--build` по умолчанию — `LastBuildSource` проекта; указанный запоминается, как в окне.
- `--version` по умолчанию — найденная `VersionDetector` (FileVersion главного exe или
  `<Product>_vers.sptv`); не нашлась — ошибка «укажите --version».
- `--overwrite` — пересборка той же версии (окно спрашивает «Перезаписать?»).
- `--dry-run` у `deliver`/`release` — показать, что и куда будет залито (метод, путь/хост+папка, число
  и объём файлов), ничего не меняя. Доставка — действие наружу, поэтому только по явной команде.
- `release` выполняет этапы по порядку и останавливается на первом провале; `--deliver` и `--verify`
  явные, без них `release` = `patch`.
- Нет FTP-реквизитов или пароль не расшифровался → ошибка «задайте реквизиты в UpdateManager
  (Выпуск → FTP-сервер…)»; CLI их не спрашивает.

## Коды выхода

| Код | Значение |
|---|---|
| 0 | Успех (для `status` — команда выполнена, состояние в выводе) |
| 1 | Ошибка аргументов или проекта (нет папки, не проект) |
| 2 | Заблокировано защитой (пустой `BaseDownloadURL`, версия ниже, нет типов патча…) |
| 3 | Нужен флаг подтверждения (перезапись, устаревшие настройки, не-ASCII…) |
| 4 | Сборка патча упала |
| 5 | Доставка упала |
| 6 | Проверка не прошла (сервер ответил, патч битый/не тот) |
| 7 | Проверка: таймаут / сервер недоступен (отдельно — см. «Сеть») |
| 130 | Прервано (Ctrl+C → `Cancel()` операции, этап не засчитан) |

## Вывод `--json`

```json
{
  "project": "D:\\ProjectsUpdates\\UpdateManager",
  "version": "2.1.0.0",
  "stages": [
    { "kind": "build",    "state": "done",    "at": "2026-11-02T18:04:00", "detail": "скопирован …" },
    { "kind": "patch",    "state": "done",    "at": "2026-11-02T18:05:12" },
    { "kind": "delivery", "state": "done",    "at": "2026-11-02T18:06:40", "method": "ftp" },
    { "kind": "verify",   "state": "failed",  "at": "2026-11-02T18:07:30", "reason": "Таймаут 30 с: …" }
  ],
  "next": "verify",
  "exitCode": 7
}
```

Состояния и тексты — из той же модели выпуска, что и каталог окна (`done` / `pending` / `failed`,
«устарела: …»). Платформа (`Windows`) — поле трека, задел под Android.

## Сеть

Роутер без NAT loopback: изнутри LAN публичный адрес сервера недоступен, проверка висит до таймаута.
Поэтому: `--timeout` у `verify` (по умолчанию как в окне), таймаут/недоступность — свой код 7, чтобы
автоматизация могла отличить «дома не проверить» от «патч битый» (код 6). FTP (192.168.0.100) доступен
только из LAN — снаружи `deliver` упадёт с кодом 5 и понятной причиной (`FtpErrorText`).

## Связка с `release.ps1`

Скрипт по-прежнему ничего не заливает сам. Новый необязательный ключ, например
`-Publish <папка проекта обновлений>`, после сборки `Release/` вызывает
`Release\umcli.exe release --project … --build Release --deliver --verify` и печатает итог.
Без ключа поведение прежнее.

## Не входит

- MCP-сервер и HTTP-API (возможное продолжение поверх CLI).
- Создание проектов, правка настроек проекта и реквизитов FTP из CLI — это делается в окне.
- Генерация RSA-ключей и заливка приватного ключа.
- Android-трек (появится в модели выпуска отдельно; CLI получит его без изменения команд).

## Тесты

- Сервис выпуска: каждая защита (`Blocked`/`NeedsConfirmation`), сброс этапов при повторе, запись дат —
  на настоящем движке, как `EnginePipelineTests` (доставка в папку, проверка через `file:///`).
- CLI: разбор аргументов, коды выхода, `--json` по схеме, `--dry-run` ничего не меняет; сквозной
  `release` на временном проекте.
- VM окна: текущие тесты без изменений поведения.
