# Методичка агенту: внедрение обновлений через UpdateManager

Назначение: внедрить систему обновлений в приложение, сохранив его стек,
архитектуру и пользовательские данные. Документ можно передать агенту вместе с доступом к исходникам
целевого проекта и UpdateManager. Все имена и адреса в примерах условные.

Область готового решения: Windows-приложения с файловым обновлением и Android-приложения,
распространяемые APK вне магазинов. Для других платформ и способов распространения сначала установи
совместимость; не обещай перенос без разработки платформенного установщика.

## 1. Задание агенту и исходные параметры

Внедри проверку, фоновую загрузку и отдельное применение обновления. Используй наш **UpdateManager**
как издатель для обеих платформ. Доведи работу до проверяемого перехода с версии A на B в тестовом канале,
документируй выпуск и явно перечисли проверки, для которых не хватило доступа или устройства.

Перед изменениями прочитай инструкции целевого репозитория, проверь ветку и незакоммиченные изменения.
Изучи существующие сборку, DI, жизненный цикл, хранение данных и установку. Не меняй стек попутно.

Составь паспорт внедрения. Значения ищи в коде и конфигурации, у владельца уточняй только отсутствующие:

| Параметр | Что зафиксировать |
|---|---|
| Платформы | Windows/Android, поддерживаемые ОС, архитектуры CPU, способ распространения |
| Идентичность | Имя проекта UpdateManager, Windows EXE, Android applicationId |
| Версии | Источник версии, числовой FileVersion, алгоритм Android versionCode |
| Артефакты | Папка публикации Windows, релизный APK, папки вывода сборки |
| Каналы | Отдельные тестовый и рабочий каналы, точные HTTPS-адреса манифестов |
| Данные | Каталоги базы, настроек, документов, логов и кэша |
| Доверие | Публичный RSA-ключ обновлений, владелец закрытого ключа, Android keystore |
| Издатель | Доступная версия UpdateManager и её настройки для обеих платформ |

Не копируй имена, префиксы настроек, applicationId, домен, хеш-канал и ключи другого продукта.
Не печатай и не коммить закрытые ключи, keystore, пароли и реквизиты публикации.
Для уже выпускаемого продукта сохраняй его идентичность, сертификат APK и действующий канал.

## 2. Архитектура и ответственность

| Компонент | Ответственность |
|---|---|
| Сборка Windows | Создаёт папку публикации с версией файлов |
| Сборка Android | Собирает APK, подписывает его релизным keystore, создаёт latest.json с SHA-256 APK |
| UpdateManager / Windows | Создаёт файловые патчи, подписывает XML-метаданные, публикует канал |
| UpdateManager / Android | Подписывает latest.json по маске и публикует APK + JSON + SIG |
| Клиент | Проверяет версию и доверие, скачивает, проверяет целостность, запускает установку |
| ОС / установщик | Windows — SelfPatcher заменяет файлы после выхода; Android — PackageInstaller |

**Две разные подписи Android:** подпись APK keystore нужна Android для установки поверх существующего
приложения. RSA-подпись манифеста нужна клиенту для доверия к версии, URL и хешу. Подпись APK остаётся
в сборке; подпись манифеста выполняет UpdateManager. Скрипт сборки больше не создаёт latest.json.sig.

Проверка, загрузка и установка — отдельные операции. Успешная загрузка не закрывает приложение
и не запускает установку автоматически. Ручную и автоматическую проверку добавляй по требованиям продукта.

## 3. Общий клиентский контракт

Размести интерфейс и модели в общем слое, реализации — в платформенных модулях. Для другого языка
сохрани семантику, адаптируя типы к его среде:

```csharp
enum UpdateState { UpToDate, UpdateAvailable, Error }
record UpdateCheckResult(UpdateState State, string? LatestVersion = null, string? Message = null);

interface IUpdateService
{
    string CurrentVersion { get; }
    Task<UpdateCheckResult> CheckAsync(CancellationToken ct = default);
    Task DownloadAsync(IProgress<double>? progress = null, CancellationToken ct = default);
    Task ApplyAsync();
}
```

Прогресс — 0..1. DownloadAsync сохраняет подготовленное обновление, ApplyAsync без него выдаёт ошибку.
Не допускай одновременных загрузок, установки во время загрузки и использования устаревшего состояния
«готово» после новой неудачной попытки. Отмена должна завершать работу и освобождать ресурсы.

Загрузкой владеет сервис или корневой координатор, живущий дольше страницы настроек. UI показывает
проверку, доступную версию, прогресс, отмену, готовность, установку и понятную ошибку с повтором.
Технические подробности идут в журнал. Не показывай «последняя версия», если проверка завершилась ошибкой.
Платформенную реализацию регистрируй существующим механизмом DI; заглушка не должна скрывать ошибку
конфигурации в релизе поддерживаемой платформы.

## 4. Версии, каналы и доверие

- Один источник продуктовой версии для UI и сборки. Windows FileVersion — числовая, монотонно растущая;
  проверь фактическую версию опубликованного EXE, которую читает UpdateManager.
- Android сравнивает установленный versionCode с манифестом, а не строки versionName.
  Сохрани существующую монотонную схему. Например, формулу MAJOR*10000 + MINOR*100 + PATCH
  можно использовать только с ограничением MINOR и PATCH до 99 и проверкой роста относительно
  уже выпущенных кодов. Иначе возможны коллизии и понижение при смене разряда.
- Номер, уже переданный пользователю или опубликованный, повторно не используй.
- Тестовый канал отдели адресом. Канал, зашитый в выпущенный клиент, должен оставаться доступным;
  перенос хостинга требует сохранения старых адресов или заранее доставленной миграции клиента.
- Публичный RSA-ключ встрой в доверенную сборку до первого выпуска. Отсутствие ключа должно быть
  ошибкой релизной конфигурации; не используй режим «нет ключа — нет проверки».
- Проверяй подпись до доверия полям манифеста; при отсутствии или неверной подписи отклоняй обновление.
  SHA-256 без доверенного манифеста не подтверждает издателя. Используй HTTPS.
- Не подменяй публичный ключ при сетевой ошибке. Ротация ключа требует отдельного плана доставки
  доверия старым клиентам. Сохрани резервные копии закрытого RSA-ключа и Android keystore у владельца.

## 5. Windows: SimplePatchTool и SelfPatcher

1. Проверь пригодность пофайлового обновления: формат публикации, права записи, дополнительные процессы,
   антивирус, блокировки файлов и способ запуска. Установку в Program Files проверь отдельно;
   не считай, что патчер автоматически решит вопрос повышения прав.
2. Подключи совместимые SimplePatchTool и SimplePatchToolSecurity из проверенного комплекта
   UpdateManager. Зафиксируй происхождение, версию/хеши и лицензию. Движок архивный: совместимость
   с новым рантаймом нужно проверять. Для приложения вне .NET требуется совместимый адаптер;
   эти DLL нельзя просто подключить к любому стеку.
3. Для .NET проверь наличие зависимости System.Security.Cryptography.Xml в публикации:
   ссылка на DLL через HintPath не переносит её зависимости автоматически. Версию выбирай под
   целевой TFM и политику зависимостей проекта, не копируй номер пакета из примера механически.
4. Собирай папкой, не single-file, для небольших файловых патчей. Пример настроек: self-contained,
   PublishSingleFile=false и PublishTrimmed=false; требования своего приложения проверь отдельно.
5. Вынеси полный URL VersionInfo.info в опции. Если есть переопределение для тестов, явно задай
   приоритет: тестовое переопределение → полный URL → адрес из частей. Проверяй итоговый адрес.
6. Создавай патчер с нужными repair/incremental/installer и silent-режимом согласно документации движка.
   Включи UseVersionInfoVerifier и UsePatchInfoVerifier с проверкой XML-подписи публичным ключом.
7. CheckAsync использует CheckForUpdates(true): Success означает доступность обновления,
   AlreadyUpToDate — актуальную версию; прочие результаты обрабатывай как ошибки.
8. DownloadAsync использует Run(true), ожидает окончания, передаёт отмену через Cancel и сохраняет
   успешный экземпляр патчера до ApplyAsync. Не блокируй UI ожиданием движка.
9. ApplyAsync вызывает ApplySelfPatch с путём SelfPatcher и правильным EXE перезапуска.
   Только после успешной передачи управления корректно закрой приложение: сохрани данные,
   останови фоновые операции и освободи файлы. SelfPatcher ждёт выхода, заменяет файлы и запускает EXE.
10. Проверь доставку SPPatcher/ самим патчем UpdateManager уже при первом обновлении.
    Не добавляй параллельную ручную схему доставки патчера без причины.

**Сохранность данных:** repair удаляет из каталога приложения файлы, которых нет в манифесте.
Базы, пользовательский контент, настройки и логи должны жить за его пределами, в каталоге данных
приложения. Если старый продукт хранит их рядом с EXE, сначала реализуй и проверь безопасный перенос
с резервной копией; не включай repair до решения этого вопроса.

Прогресс движка может начинаться заново для каждого инкрементального патча. Для цепочки рассчитывай
общий прогресс с весами по размерам. Если для этого используются приватные поля движка через
рефлексию, это привязка к конкретной DLL, требующая теста совместимости. При переходе incremental →
repair отображай смену этапа; не обещай бесшовную полосу при смене метода.

## 6. Android: APK и PackageInstaller

1. Сохрани applicationId и релизный сертификат установленного приложения. Подготовь APK нужной ABI
   с более высоким versionCode; не используй AAB как файл для прямой установки.
2. Сборка подписывает APK keystore, вычисляет SHA-256 **готового подписанного APK**, затем создаёт
   latest.json в UTF-8 без BOM. Удаляет старый latest.json.sig, но новую RSA-подпись не создаёт.
3. Используй контракт манифеста:

```json
{
  "versionCode": 10203,
  "versionName": "1.2.3",
  "apkUrl": "https://updates.example.org/product/test/AndroidPatch/Product.apk",
  "sha256": "<64 шестнадцатеричных символа SHA-256 готового APK>"
}
```

Это шаблон; URL и хеш заменяются реальными значениями сборки. Генерация sha256
и его проверка клиентом обязательны для этой интеграции.

4. UpdateManager подписывает сырые байты latest.json: RSA-SHA256, PKCS#1 v1.5;
   latest.json.sig содержит base64 подписи. Клиент проверяет те же байты до декодирования,
   удаления BOM и разбора JSON. После подписи нельзя менять пробелы, переносы или кодировку.
5. Проверяй подпись обязательно, затем сравнивай versionCode с установленным. URL APK бери из
   проверенного манифеста; политика сети должна разрешать только предусмотренный HTTPS-транспорт.
6. Скачивай в app-private cache. Кэш связывай с версией и ожидаемым хешем; проверяй перед повторным
   использованием, удаляй неполные и повреждённые файлы. Состояние «готово» выставляй после проверки.
7. Для продолжения при сворачивании используй подходящий платформенный механизм. Один из вариантов —
   foreground-служба dataSync, уведомление с прогрессом и отменой, partial wake-lock.
   Согласуй разрешения и жизненный цикл с targetSdk целевого проекта; проверь итоговый manifest.
   Учти INTERNET, REQUEST_INSTALL_PACKAGES и разрешения выбранного механизма фоновой работы.
   Fallback на загрузку в процессе не гарантирует продолжение после ухода приложения в фон.
8. ApplyAsync проверяет разрешение установки из неизвестных источников, при необходимости открывает
   системные настройки. После выдачи разрешения пользователь должен иметь возможность повторить установку.
9. Передай APK потоком в PackageInstaller Session API вне UI-потока. Подключи receiver результата
   с уникальным action своего продукта; проверь доступность receiver и необходимость Exported=false. При STATUS_PENDING_USER_ACTION
   запусти полученный системный Intent подтверждения. Различай передачу сессии и успешную установку.
10. Проверь отказ пользователя, ошибки установки, повтор, возврат из настроек и сохранность данных.
    Android управляет установкой и закрытием процесса; автоматический перезапуск не обещай без проверки.

Не удаляй установленное приложение ради обхода конфликта сертификатов: это может стереть данные.
Смена keystore и несовпадение applicationId не исправляются подписью манифеста.

## 7. Настройка UpdateManager и публикация

Работай в отдельном проекте обновлений нового продукта. Проверь реальную версию UpdateManager:
названия полей и доступные операции сверяй с её кодом или интерфейсом. Не считай старые заметки
о ветках издателя доказательством текущих возможностей.

**Windows:** задай папку билда, имя проекта, BaseDownloadURL, файловые методы патчинга,
IsSelfPatchingApp и RSA-подпись. Публикуемый VersionInfo.info и ссылки внутри него должны вести
в один выбранный канал. Сохраняй версии и историю, необходимые для цепочек патчей.

**Android:** выбери Android-платформу проекта, папку с APK и latest.json, маску подписи latest.json,
RSA-ключ, соответствующий встроенному публичному ключу. UpdateManager подписывает выбранные файлы
по маске; не рассчитывай, что он сам создаст манифест или исправит его поля. Он публикует вместе
APK, latest.json и latest.json.sig. Исключи APK эмулятора и остальные вспомогательные файлы.

По умолчанию AndroidPatch/ находится внутри канала рядом с Windows VersionInfo.info. При такой
раскладке проверь правила сохранения соседних каталогов (keepNames): очистка Windows-публикации
не должна удалять Android. Закрытые ключи не должны попадать в публичный каталог или артефакты.

До рабочего выпуска проверь способ переключения набора файлов на сервере. Клиент не должен получать
новый JSON со старым SIG или APK. Используй поддерживаемую издателем атомарную выкладку и проверь её
поведение; наличие трёх файлов само по себе не доказывает атомарность. Для CDN проверь кеширование
манифестов, подписи и APK; предпочтительны неизменяемые URL артефактов, если издатель их поддерживает.

Публичные адреса проверяй без издательских реквизитов: HTTP 200, корректное содержимое, подписи,
хеш APK, ссылки внутри XML/JSON. Не выдавай страницу HTML или авторизации за успешную проверку URL.

## 8. Приёмка на двух версиях

Собери A и B с одной идентичностью и ключами, B > A. Установи A обычным способом, создай тестовые
пользовательские данные, опубликуй B в тестовый канал. Обновляй через UI приложения, а не ручной
заменой файлов. Для Windows дополнительно проверь переход через несколько промежуточных версий.

| Сценарий | Ожидаемый результат |
|---|---|
| Сервер отдаёт текущую/более старую версию | Обновление не предлагается |
| Проверка B из A | Видна правильная новая версия |
| Уход со страницы настроек | Загрузка и прогресс продолжаются |
| Отмена, обрыв сети, повтор | Приложение работает, можно повторить, частичный файл не готов к установке |
| Нет/неверна подпись, изменён JSON/XML | Обновление отклонено |
| Повреждён APK/патч | Проверка целостности отклоняет файл |
| Повторная загрузка | Валидный кэш переиспользуется, повреждённый скачивается заново |
| Apply до завершения Download | Установка не запускается |
| Windows: цепочка и repair | Корректный итоговый набор файлов и версия, понятный прогресс |
| Windows: второй процесс, нет прав/места | Понятная ошибка, данные сохранены |
| Android: сворачивание/погасший экран | Проверено поведение загрузки на поддерживаемых ОС |
| Android: разрешение/отказ установки | Есть понятный путь повтора, ложного успеха нет |
| Установка B | Версия B, данные и настройки сохранены, приложение запускается |
| Повторная проверка из B | Обновление не предлагается |
| Публикация одной платформы | Канал другой платформы сохраняется |

Автотестами покрой состояния координатора, сравнение версий, отмену, подпись, хеш и прогресс.
Реальную замену работающего Windows-приложения и системную установку Android проверь отдельно.
Если платформа недоступна, укажи её как непроверенную, а не принимай внедрение целиком.
Отдельно опиши восстановление при сбое установки и совместимость миграций данных.
Не обещай автоматический rollback: он должен быть явно реализован и проверен.

## 9. Что оставить в целевом проекте

- Реализацию, конфигурацию каналов и публичный ключ; закрытые материалы остаются у издателя.
- Воспроизводимые команды сборки и повышения версии, генерацию Android-манифеста без подписи.
- Короткую инструкцию выпуска через UpdateManager: папки, маски, исключения, адреса, проверки.
- Описание хранения данных, ограничений прав, восстановления, хранения и ротации ключей.
- Результаты A → B: ОС/ABI, версии, сценарии, проверки подписей и сохранности данных.
- Список непроверенного и необходимых действий владельца. Изменения коммить по правилам проекта;
  публикацию в рабочий канал выполняй в пределах полученного разрешения.

## 10. Карта компонентов интеграции

Найди соответствующие компоненты в целевом проекте или согласованном примере интеграции.
Имена ниже — условные ориентиры, а не обязательные пути и не готовые ссылки на внешний проект.
Перед переносом сверяй актуальный код: старые исследовательские документы могут описывать заменённые решения.

| Назначение | Типовые компоненты |
|---|---|
| Общий контракт | `IUpdateService`, модели состояния обновления |
| Версия и прогресс цепочки | Источник версии приложения, расчёт общего прогресса |
| Windows-клиент | Сервис обновлений Windows, опции канала, публичный ключ |
| Android-клиент | Сервис обновлений Android, публичный ключ |
| Android фон и установка | Служба загрузки, обработчик результата PackageInstaller |
| Сборка и версии | Скрипты сборки, повышения версии и генерации манифеста |
| Примеры тестов | Прогресс цепочки, канал обновлений, состояния UI |
| Проектные подробности | Описание самообновления и порядка выпуска целевого продукта |

UpdateManager — отдельный репозиторий владельца. Для адаптации издательской стороны нужен доступ
к нему; клиентские исходники не заменяют проверку его настроек и алгоритма публикации.
