## Как подключить обновления

Эта инструкция — для владельца приложения и разработчика, который настраивает обновления впервые.
Она описывает подготовку самого приложения и выпуск через UpdateManager. Одних настроек издателя
недостаточно: в приложение нужно добавить проверку, скачивание и установку обновления.

### С чего начать

UpdateManager готовит и публикует обновления. Ваше приложение обращается к серверу, проверяет
доступную версию, скачивает файлы и предлагает установить их. Windows обновляется файловым патчем;
Android — установкой нового APK поверх прежнего приложения. Для других платформ потребуется отдельное решение.

- Определите, что выпускаете: Windows, Android или обе платформы. Для Android здесь рассматривается
  распространение APK вне магазинов.
- Выберите постоянное имя продукта и адрес HTTPS для обновлений. Отдельно заведите тестовый канал,
  чтобы проверять новую сборку до публикации для пользователей.
- Решите, где приложение хранит базу, документы, настройки и логи. Эти данные должны сохраняться
  после обновления; в Windows храните их вне папки с программой.
- Договоритесь с разработчиком, откуда берётся версия, куда сборка складывает готовые файлы и кто
  хранит ключи. Укажите путь к главному EXE Windows и идентификатор приложения Android (applicationId).

**Что передать разработчику:** исходники приложения, поддерживаемые платформы, адрес тестового канала,
способ сборки и сведения о хранении данных. Для подробного задания используйте отдельную методичку
UPDATE_SYSTEM_AGENT_GUIDE.md из документации проекта.

### Версии и ключи

Версия должна повышаться при каждом опубликованном обновлении. Уже выпущенный номер повторно
не используйте. Например, после 1.2.3 можно выпустить 1.2.4.

- **Windows:** главный EXE должен содержать числовую FileVersion, например 1.2.4.0. Проверьте её
  у готовой сборки. Если используете файл версии движка, он называется <ИмяПроекта>_vers.sptv.
- **Android:** versionName — понятный человеку номер, например 1.2.4; versionCode — целое число,
  которое Android использует для сравнения версий. Новый APK должен иметь больший versionCode.
  Схему его вычисления согласуйте с разработчиком и не меняйте без проверки старых выпусков.
- **RSA-ключ обновлений:** в UpdateManager создайте пару ключей. public.key передайте разработчику
  для включения в приложение. private.key храните у издателя, с резервной копией; на публичный сервер
  и в репозиторий он попадать не должен. Клиент должен отклонять обновления без верной подписи.
- **Ключ Android keystore:** это отдельный ключ, которым сборка подписывает APK. Для обновления
  поверх установленного приложения сохраняются прежние applicationId и сертификат APK.

У Android две подписи: keystore подтверждает APK для системы, RSA-подпись манифеста подтверждает
сведения об обновлении для клиента. Одна подпись не заменяет другую. Смена ключа уже выпущенного
продукта требует отдельного плана; потеря keystore не исправляется новым RSA-ключом.

### Подготовка Windows

Разработчик добавляет в приложение клиент SimplePatchTool и проверку подписей. UpdateManager
не встраивает этот код автоматически. Для приложения вне .NET может потребоваться адаптер.

Подробные примеры подключения клиента, описание API и структуры движка:

- [Документация SimplePatchTool (Wiki)](https://github.com/yasirkula/SimplePatchTool/wiki).
- [Подключение самообновления: Self Patching App Tutorial](https://github.com/yasirkula/SimplePatchTool/wiki/Self-Patching-App-Tutorial).
- [Исходный код SimplePatchTool на GitHub](https://github.com/yasirkula/SimplePatchTool).
- [Репозиторий UpdateManager на GitHub](https://github.com/BorisBaNaNa/UpdateManager).

Примеры API сверяйте с DLL, поставляемыми с UpdateManager: проект движка архивный, а исторические
инструкции издателя могут отличаться от текущего интерфейса UpdateManager.

- Собирайте приложение в отдельную папку публикации. Для пофайловых патчей используйте обычные
  файлы, а не единый single-file. Совместимость библиотек и зависимостей проверьте на вашем .NET.
- В клиенте задайте полный HTTPS-адрес VersionInfo.info и публичный RSA-ключ. Включите проверку
  подписей VersionInfo и PatchInfo до использования их содержимого.
- Сделайте три понятных действия: проверить наличие новой версии, скачать её с прогрессом и
  отменой, затем установить. Успешное скачивание само по себе не должно закрывать приложение.
- При установке клиент передаёт управление SelfPatcher, сохраняет данные и закрывается. Патчер
  заменяет файлы и запускает новую версию. В UpdateManager используется SPPatcher/SelfPatcher.exe;
  проверьте, что патчер доставляется клиенту уже при первом обновлении.
- Проверьте права записи в папку установки, особенно в Program Files. Наличие патчера не означает,
  что приложение автоматически получает права администратора.

**Сначала защитите данные.** Repair-патч может удалить из папки программы файлы, которых нет в
манифесте. Если база или настройки сейчас лежат рядом с EXE, поручите разработчику перенести их
в каталог данных с резервной копией до включения такого обновления.

### Подготовка Android

Разработчик собирает релизный APK с прежним applicationId, прежним сертификатом и увеличенным
versionCode. AAB не подходит как файл для прямой установки.

Рядом с готовым подписанным APK сборка должна создавать latest.json. Он содержит четыре поля:

- **versionCode:** целый код новой версии, например 10204.
- **versionName:** строка с номером выпуска, например "1.2.4".
- **apkUrl:** полный публичный HTTPS-адрес именно этого APK, например
  https://updates.example.org/product/test/AndroidPatch/Product.apk.
- **sha256:** SHA-256 готового подписанного APK — строка из 64 шестнадцатеричных символов.

Это примеры: замените адрес и значения данными своего приложения. UpdateManager не создаёт
latest.json и не исправляет в нём URL или хеш. Сборка удаляет старую latest.json.sig, а новую
RSA-подпись создаёт UpdateManager при подготовке выпуска. После подписи JSON менять нельзя.

- В клиенте задайте HTTPS-адрес latest.json и публичный RSA-ключ. Клиент сначала проверяет подпись
  исходных байтов JSON, затем читает поля и сравнивает versionCode с установленной версией.
- Скачанный APK храните в кэше приложения. До предложения установки клиент обязан проверить SHA-256;
  повреждённую или недокачанную копию устанавливать нельзя.
- Установка выполняется системным установщиком Android через PackageInstaller. Пользователю может
  понадобиться разрешить установку из этого источника и подтвердить установку в системном окне.
- Разработчик должен обеспечить повтор после отказа или выдачи разрешения. Если загрузка должна
  продолжаться при сворачивании приложения, её фоновую работу нужно отдельно реализовать и проверить.

Не удаляйте старое приложение ради обхода ошибки сертификата: можно потерять его данные.
Установку, отказ пользователя и сохранность данных проверьте на настоящем устройстве.

### Настройка UpdateManager

Создайте отдельный проект обновлений для своего приложения. Папка проекта UpdateManager и папка
готовой сборки должны быть разными. Сохраняйте проект между выпусками: в нём история версий и ключи.

- В настройках проекта включите нужные платформы. Если Windows и Android включены вместе,
  Android выпускается под версией Windows. Для независимых номеров используйте отдельные проекты.
- Задайте BaseDownloadURL — публичный HTTPS-адрес папки патчей с завершающим слешем. Клиент Windows
  должен обращаться к VersionInfo.info именно в этом канале. Если используется дополнительный
  каталог загрузки, проверьте итоговые URL внутри манифеста.
- Для Windows выберите папку публикации и главный EXE, включите режим самообновляемого приложения
  (IsSelfPatchingApp), нужные виды патчей и RSA-подпись. Подготовьте ключи, соответствующие public.key клиента.
- Для Android выберите папку с APK и latest.json. Включите «Подписывать файлы RSA-ключом» и укажите
  маску latest.json. Исключите APK эмулятора и вспомогательные файлы через «Не выкладывать».
- Android-канал по умолчанию — AndroidPatch внутри папки патчей. Клиентский адрес latest.json и
  apkUrl должны вести в фактическое место публикации этих файлов.
- Выберите способ доставки: папка или FTP. Реквизиты FTP задаются в UpdateManager; клиенту они
  не нужны — он скачивает обновления по публичному HTTPS-адресу.

В отдельном Android-проекте версия берётся из versionName в JSON-манифестах папки сборки и подпапок.
Если допустимая версия не найдена или манифесты содержат разные версии, программа попросит ввести её.
versionCode не является номером выпуска в каталоге UpdateManager.

### Первый выпуск и проверка

Сначала проведите весь путь в тестовом канале. Нужны две сборки: установленная A и более новая B,
с одной идентичностью и ключами. В A создайте тестовые данные.

- Выберите папку готовой B. После пересборки нажмите кнопку сканирования справа от «ВЫПУСКИ»,
  чтобы UpdateManager перечитал файлы без перезапуска.
- Для Windows выполните «Создать патч». Для Android — «Подписать файлы»: программа сохранит
  выкладку версии и создаст подпись манифеста.
- Выполните «Доставить», затем «Проверить». Проверка действительно скачивает опубликованные
  файлы. Она не заменяет проверку установки в вашем приложении.
- В установленной A найдите B через интерфейс обновлений, скачайте и установите её. Убедитесь,
  что запускается B, данные и настройки сохранены, а повторная проверка не предлагает ту же версию.
- Проверьте отмену и обрыв загрузки, повтор, неверную подпись и повреждённый файл. В Windows
  проверьте цепочку нескольких версий, repair и ограничения прав; в Android — сворачивание,
  разрешение установки, отказ и повтор.
- Выпуская одну платформу, убедитесь, что канал другой сохранился. Если используется CDN,
  проверьте, что клиент не получает новый JSON со старой подписью или APK из кэша.

**Доставка зеркальная:** в папке назначения старые файлы могут удаляться. Выделите для обновлений
отдельную папку, не храните там посторонние данные. Не используйте рабочий канал для первой пробы.

### Если что-то не работает

- **Версия не появилась:** проверьте папку сборки и нажмите сканирование у «ВЫПУСКИ». В Windows
  проверьте FileVersion главного EXE или файл версии; в Android — строку versionName в JSON и
  отсутствие противоречащих манифестов. При двух платформах ориентируйтесь на версию Windows.
- **Файлы не скачиваются:** откройте публичные адреса без FTP-реквизитов. Сервер должен отдавать
  сами XML, JSON и APK, а не страницу входа или HTML-ошибку. Сверьте BaseDownloadURL и ссылки.
- **Ошибка подписи:** проверьте соответствие публичного ключа клиента закрытому ключу издателя.
  JSON мог измениться после подписи. Не отключайте проверку и не меняйте ключ наугад.
- **Android не устанавливает APK:** проверьте applicationId, сертификат, рост versionCode,
  архитектуру устройства и разрешение установки из этого источника.
- **Windows не заменяет файлы:** проверьте права, свободное место, дополнительные процессы
  приложения и наличие SelfPatcher. Сохраните журнал ошибки для разработчика.
- **После обновления пропали настройки:** остановите дальнейшую публикацию, проверьте каталог
  данных, резервную копию и миграции. Восстановление должно быть предусмотрено разработчиком.

К выпуску готовы, когда переход A → B проверен через само приложение, данные сохранены,
подписи проверяются, а непроверенные платформы и ограничения записаны явно.
