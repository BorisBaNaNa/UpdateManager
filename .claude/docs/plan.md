# План UpdateManager

Текущая версия — **2.0.0** (тег `v2.0.0`, 2026-10-28). Схема версий — SemVer из трёх чисел:
новая возможность → minor, иначе patch. Каждый выпуск — тег `vX.Y.Z` (см. `CLAUDE.md`).

## Дальше

### Сквозная проверка самообновления — с 2.0.1

- Полный цикл версии N → N+1: тихая проверка при старте → `Run(true)` в кэш → `SPPatcher\SelfPatcher.exe`
  подменяет файлы → перезапуск уже новой версии. Тестами не покрыт.
- Частично проверено на выпуске 2.0.0: скачивание и применение прошли (тогда докачивался сам self-patcher,
  это исправлено — он лежит в `Release/SPPatcher`). Целиком — на обновлении до 2.0.1.
- Проверку по публичному адресу делать из внешней сети (у роутера нет NAT loopback), FTP — только из LAN.

### CLI выпуска `umcli` — 2.1.0, спек готов, не начато

- Вынести логику выпуска (защиты, сборка + подпись, доставка, проверка, запись и сброс этапов) из
  `MainWindowViewModel` в Core (`Core/Release/`); окно — клиент сервиса.
- Консольный `src/UpdateManager.Cli` → `umcli.exe` рядом с `UpdateManager.exe`: `status`, `patch`,
  `deliver`, `verify`, `release`; вопросы окна — флаги; коды выхода; `--json`; `--dry-run` у доставки.
- Необязательная связка с `scripts/release.ps1` (`-Publish`).
- Спек: `docs/superpowers/specs/2026-10-28-cli-release-design.md`.

### Android-проекты — идея, спека нет

- Без патчей: билд (apk) → файлы сервера (версия, лицензия) → доставка → проверка.
- Один выпуск может нести несколько платформ (Windows и Android одной версии вместе).
- Модель выпуска к этому готова: `PlatformTrack` на платформу, этап «Файлы» (`StageKind.Files`)
  и его цвет в дизайне уже есть. Нужны: формат файлов версии/лицензии, тип проекта, проверка для apk.
- Контекст: `PRODUCT.md` (Capabilities and Constraints).

### FTPS/TLS для доставки — при необходимости

- Сейчас только обычный FTP (сервер в LAN). FluentFTP умеет FTPS — добавить опцию в реквизиты.

- Новый дизайн всех окон — мир «каталог» (`DESIGN.md`): каталог выпусков, этапы Билд → Патч → Доставка →

- Даты сборки патча, доставки и итог проверки по версиям (`updatemanager.project.xml`).
- Самообновление (клиентская часть, пресет для билда самого UpdateManager; URL и ключ —
  `appsettings.json`). Спек: `docs/superpowers/specs/2026-10-27-self-update-design.md`.
- Выпуск скриптом `scripts/release.ps1` (тесты → версия → publish в `Release/` → version holder), один
  self-patcher в `SPPatcher\`.

### 1.x — WinForms (ветка `v1`, последний тег `v1.0.3`)

Исходный план 1.x выполнен, кроме шага 7:

- движок SimplePatchTool подключён (CLR 2.0 DLL, работает и под .NET 10);
- сборка патча (repair / installer / incremental, сжатие, IgnoredPaths) с логом;
- пресеты JSON заменены **проектами**, как в IDE (папка движка + `updatemanager.project.xml`, недавние);
- FTP-заливка на FluentFTP с прогрессом, реквизиты в профиле пользователя, пароль — DPAPI;
- «Проверить» — не HTTP-проба, а настоящая закачка клиентом движка во временную папку;
- RSA: генерация ключей, подпись манифестов, заливка приватного ключа коллегам в закрытую FTP-папку.

## Отказались

- **Обновление ссылок в готовом `VersionInfo.info` (`PatchUpdater`, шаг 7 плана 1.x).** Нужно было бы,
  если `BaseDownloadURL` нельзя задать при сборке. Вместо этого сборка блокируется при пустом адресе,
  итоговый адрес виден в настройках, а «Проверить» ловит неверный. Вернуться, если появится реальный случай.
- **Анимация заливки блока этапа.** Каталог пересобирается после каждого действия — переход цвета не
  сыграл бы без переделки модели выпуска, а для инструмента, который открывают раз в несколько недель,
  это не окупается. Правило «без движения» — `DESIGN.md` (The Still Catalog Rule).
